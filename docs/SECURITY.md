# Security

This document describes what the SCP:SL Trust Network protects against, how, and where the controls
live in the code. The binding protocol details are in [ARCHITECTURE.md](./ARCHITECTURE.md) (§5 server
authentication, §9 audit, §12 web authentication and RBAC, §14 API controls, §15 logging).

## 1. Assets and trust boundaries

| Asset | Why it matters |
|---|---|
| Case history, verdicts, reports, appeals | the platform's credibility; must not change silently (R7) |
| Evidence files and their review status | integrity and restricted access |
| Server private keys (on SCP:SL servers only) | whoever holds one can speak for that server |
| Staff accounts (reviewer … super_admin) | can set verdicts, review evidence, change roles |
| Player data (identifiers, nicknames, network hashes) | privacy ([PRIVACY.md](./PRIVACY.md)) |
| Audit log | accountability of every privileged action (R8) |

Trust boundaries: SCP:SL servers and browsers are **untrusted clients**. Everything they send is
validated (zod schemas on params, query, body *and* responses), authenticated (Ed25519 signature or
session) and authorized (RBAC + server-team membership) by the backend (R10). The backend host,
PostgreSQL, Redis and the storage backend are trusted infrastructure.

## 2. Threats and controls

### 2.1 Malicious or compromised SCP:SL server

A server operator can send arbitrary data with a valid signature.

* **No enforcement authority**: the backend never returns or pushes an action (R1); each server's
  policy only affects that server. A malicious server cannot ban anyone elsewhere.
* **Reports ≠ verdicts**: in-game reports create/attach cases with verdict `unknown`; only reviewers
  set verdicts, and `confirmed` requires evidence verified for authenticity *and* cheating
  (`INSUFFICIENT_EVIDENCE`). Report counts never change verdicts (`backend/src/modules/cases`,
  `backend/src/modules/reports`).
* **Confirmations are counted per server and per owner** (`independent_confirmed_servers`), are shown
  as information only and never change a verdict; admins mark trusted servers (`is_trusted`).
* **Untrusted hints**: `account_created_at` is only a `server_reported` fallback; IPs are hashed on
  arrival; `server_id` in a body must match the signed header (`SERVER_ID_MISMATCH`).
* **Size and rate limits**: JSON body limit 1 MiB (in-game reports 128 KiB), 600 requests/min per
  server (`RATE_LIMIT_PLUGIN_PER_MINUTE`), per-user/IP limits elsewhere (`backend/src/http/rate-limit.ts`).
* **Suspension / revocation** of a server or single keys by admins (`POST /servers/{id}/status`,
  `POST /servers/{id}/keys/{keyId}/revoke`), audited.

### 2.2 Stolen server key

* **Keys never leave the server** (R9): generated by the plugin (`plugin/src/ScpslTrust.Core/Security`),
  stored in `identity.json` with mode 0600; only public keys are transmitted, and registration and rotation
  require proof of possession (`SCPSL-TRUST-REGISTER-V1` / `SCPSL-TRUST-ROTATE-V1` signatures).
* **Registration tokens** are single-use, stored hashed, valid 24 h (`REGISTRATION_TOKEN_TTL_HOURS`);
  creating a new one revokes the previous one.
* **Revocation** takes effect on the next request (`KEY_REVOKED`); **rotation** (`trust rotatekey`, or
  requested by an admin via heartbeat `key_rotation_requested`) keeps the old key only for
  `KEY_ROTATION_GRACE_SECONDS` (600 s). A leaked key is contained by: revoke key → new registration token →
  `trust register` on the real server. See [SERVER_REGISTRATION.md](./SERVER_REGISTRATION.md).
* A stolen key allows impersonating that one server until revoked; every request is logged with
  `server_id` and `request_id` and failures are counted.

### 2.3 Replay and request tampering

`backend/src/auth/server-auth.ts` (canonical string: `shared/src/signing.ts`, C#: `RequestCanonicalizer`):

* Ed25519 signature over `SCPSL-TRUST-V1`, method, path **with query**, `server_id`, timestamp, nonce,
  request id and SHA-256 of the **raw body** (captured before parsing, `backend/src/http/raw-body.ts`) —
  any change to path, query or body invalidates the signature.
* Timestamp window `SIGNATURE_MAX_SKEW_SECONDS` (60 s) → `TIMESTAMP_OUT_OF_RANGE`.
* Nonce stored in Redis with `SET NX` for 2 × skew + 30 s → `REPLAYED_NONCE`; request id stored for 10 min →
  `DUPLICATE_REQUEST_ID` (`backend/src/auth/nonce-store.ts`). Both are stored only *after* a valid signature,
  so unauthenticated traffic cannot fill the store.
* Repeated authentication failures per claimed server and per client → `429` before any database work
  (`RATE_LIMIT_SERVER_AUTH_FAILURES_PER_MINUTE`).
* Web side: MFA tokens, e-mail verification and password-reset tokens are single-use; TOTP steps cannot be
  reused (`totp_last_used_step`).

Operational requirement: proxies must not rewrite the path/query/body (see
[DEPLOYMENT.md §1](./DEPLOYMENT.md#1-topology)); Redis must be persistent enough to survive restarts
within the replay window (AOF in `docker-compose.prod.yml`).

### 2.4 Malicious web user

* **Sessions** (`backend/src/auth/user-session.ts`): 32 random bytes in an `HttpOnly; SameSite=Lax; Secure`
  signed cookie, only the SHA-256 stored; new session on every login; absolute (168 h) and idle (720 min)
  lifetimes; password/2FA changes revoke other sessions; users can list and revoke sessions.
* **CSRF** (`backend/src/auth/csrf.ts`): HMAC token bound to the session, required in `X-CSRF-Token` for
  every state-changing request; `Origin`/`Referer` must match `WEB_ORIGIN`; CORS only for `WEB_ORIGIN`.
* **Passwords** (`backend/src/lib/passwords.ts`): Argon2id (m = 19456 KiB, t = 2, p = 1), 10–128 chars,
  not equal to e-mail/username; unknown e-mail and wrong password return the same error with equal timing
  (dummy hash verification).
* **Lockout and throttling**: 10 auth requests/min per IP; after `LOGIN_MAX_FAILURES` (5) the account is
  locked for 15 min × 2^(n−5), max 24 h (`USER_LOCKED` audited).
* **2FA** (`backend/src/auth/totp.ts`): TOTP (RFC 6238) + 10 single-use recovery codes (stored hashed);
  TOTP secrets encrypted at rest (AES-256-GCM, `DATA_ENCRYPTION_KEY`, `backend/src/lib/crypto.ts`).
  Roles in `REQUIRE_2FA_ROLES` cannot use any route except `/auth/*` and `/me` until enrolled
  (`MFA_ENROLLMENT_REQUIRED`); setting a verdict requires an MFA-verified session.
* **RBAC** (`backend/src/auth/rbac.ts`, matrix in `shared/src/permissions.ts`): checked on every route;
  server-scoped actions require membership with an adequate team role; the UI only hides controls (R10).
  An automated authorization-matrix test checks that every protected route rejects unauthorized roles.
* **Output control**: response schemas strip internal fields; errors never contain stack traces or SQL.
* **Browser hardening**: `@fastify/helmet` on the API (strict CSP, HSTS when `COOKIE_SECURE`), and CSP with
  a script hash, `frame-ancestors 'none'`, `nosniff`, `X-Frame-Options DENY` on the panel (`web/nginx.conf`).
* **Uploads**: MIME type sniffed from magic bytes against an allow-list (`415 UNSUPPORTED_MEDIA_TYPE`),
  size limit `EVIDENCE_MAX_BYTES`, sanitized filenames; downloads use `Content-Disposition: attachment`,
  `nosniff`, `Content-Security-Policy: sandbox; default-src 'none'`, `Cache-Control: private, no-store`.
* **Proof API brute force**: 30-bit codes, ±1 window, 20 requests/min (`PROOF_RATE_LIMIT_PER_MINUTE`);
  invalid answers do not reveal which field was wrong; callers without `proof:view_code` never see the
  expected code.
* **Report spam**: 10 reports/hour per user, one open report per reporter and player.

### 2.5 Evidence tampering

* SHA-256 computed while streaming the upload (`backend/src/storage/hashing-stream.ts`) and stored with the
  row; `GET /evidence/{id}?verify=true` re-hashes the stored object.
* Database trigger: evidence rows cannot be deleted; hash, size, MIME type, storage key, URL, uploader,
  case and type cannot be updated; `superseded_by_evidence_id` can be set only once
  ([DATABASE.md §3](./DATABASE.md#3-protection-triggers-r7-r8)). Replacement creates a new row
  (`POST /evidence/{id}/supersede`), history stays visible.
* Evidence reviews are append-only (`evidence_reviews`: no UPDATE/DELETE); the three assessments
  (identity, authenticity, cheating) are independent and never change the verdict by themselves (R2).
* Access: metadata and content only for `evidence:view` holders, the uploader and members of the
  uploading server; every content access and download ticket is audited (`EVIDENCE_ACCESSED`); download
  tickets for `<video>`/`<a>` are signed with `JWT_SECRET` and valid 60 s.
* Storage: the backend never deletes objects; use a private bucket with versioning/object lock
  ([DEPLOYMENT.md §6](./DEPLOYMENT.md#6-evidence-storage)).

### 2.6 Insider (reviewer, moderator, admin)

* **Conflict of interest**: a reviewer who reported on a case cannot set its verdict; an appeal cannot be
  decided by the verdict setter or a reporter (`CONFLICT_OF_INTEREST`) unless a `super_admin` explicitly
  overrides it, which is recorded and audited.
* **Append-only history** (R7): cases, reports, reviews, confirmations, appeals, whitelist requests,
  bypasses and policy versions cannot be deleted (triggers raise SQLSTATE `TN403`, also for `TRUNCATE`).
* **Audit hash chain** (R8, `backend/src/modules/audit/service.ts`): every privileged action is written in the
  same transaction as the change, serialized by an advisory lock, each event hashing the previous one
  (`prev_hash` unique → no forks). `GET /admin/audit/verify` and `verify-audit` report the first broken
  `seq`. The runtime database role cannot UPDATE/DELETE/TRUNCATE `audit_events` and does not own the
  tables, so it cannot disable triggers ([DEPLOYMENT.md §5](./DEPLOYMENT.md#5-database-roles-and-migrations)).
* **Least privilege roles**: `admin` can manage users up to `moderator`; only `super_admin` manages admins.
  Public pages show reviewers only as pseudonyms (`Reviewer #184`).

### 2.7 Secrets and logging

* Production refuses to start with missing, weak, repeated or placeholder secrets
  (`backend/src/lib/secret-strength.ts`, `backend/src/config.ts`).
* Logs are JSON with redaction of authorization/cookie/signature/CSRF headers and every
  `password`, `token`, `secret`, `private_key`, `mfa_token`, `seed`, `signature`, `code` and `ip` field; bodies are never logged;
  client IPs only as network hashes and only with `LOG_CLIENT_IP=true` (`backend/src/lib/logger.ts`,
  `backend/src/http/logging.ts`). Audit metadata never contains passwords, tokens, keys, raw IPs or evidence content.
* The plugin never logs private keys, signatures or full IPs.

## 3. What is NOT protected

* **A compromised backend host or database superuser** can read and change everything: it holds the
  secrets (`DATA_ENCRYPTION_KEY`, `IP_HASH_SECRET`, `SESSION_SECRET`), can rewrite the audit chain from any
  point (the chain detects edits, it cannot prevent a full recomputation — export `hash` values to an
  external system periodically if you need that), and can serve arbitrary responses to plugins.
* **A compromised SCP:SL server host** exposes that server's private key (§2.2) and its local decisions.
* **Evidence authenticity** is a human assessment. Hashes prove the file was not changed *after upload*,
  not that the recording is genuine.
* **Overwatch proofs** prove that a code belongs to a session/time window (R6); they are only as reliable as
  the server that ran the session. After `RETENTION_OVERWATCH_SECRETS_DAYS` proofs can no longer be verified.
* **Network hashes** are keyed (HMAC) but IPv4 space is small: anyone with `IP_HASH_SECRET` can recover IPs
  by brute force. Protect the secret like a password database.
* **Availability** against large DDoS attacks is out of scope (use your provider's protection); rate limits
  protect against abuse, not volumetric attacks.
* **Client devices** of staff (malware, stolen unlocked sessions) — mitigated only by 2FA, session lifetimes
  and session revocation.
* **VPN / account-age / alt signals** are heuristics; they are signals by design (R3–R5), not evidence.

## 4. Reporting a security issue

Please do not open a public issue for vulnerabilities. Report privately to the maintainers of the
deployment you are using (for this repository: a private GitHub security advisory, "Report a
vulnerability" on the repository's Security tab) with steps to reproduce, affected version/commit and
impact. Do not access other users' data or disrupt production instances while testing. We aim to
acknowledge reports within a few days and to coordinate disclosure after a fix is available.

Operators: if you suspect a compromised server key, revoke it immediately (web panel → server → keys)
and re-register; if you suspect a compromised staff account, disable it (`PATCH /admin/users/{id}` with `status: disabled`,
which revokes its sessions) and review its actions in the audit log
(`GET /admin/audit?actor_type=user&actor_id=<user id>`).
