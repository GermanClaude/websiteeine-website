# Contributing

Thanks for wanting to improve the SCP:SL Trust Network. Please read
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) before a first non-trivial change — it is the
binding contract for this repository, not background reading (see
[The architecture document](#the-architecture-document-is-the-contract) below).

By participating you agree to the [Code of Conduct](CODE_OF_CONDUCT.md). Security problems go
through [SECURITY.md](SECURITY.md), never through a public issue or PR.

## Prerequisites

| For | You need |
|---|---|
| Everything TypeScript | Node.js ≥ 22 and pnpm 10 (`corepack enable` picks the pinned version from `packageManager`) |
| Backend tests | PostgreSQL 16 and Redis 7 reachable locally (`docker compose up -d postgres redis` is enough) |
| Plugin | .NET SDK 8 and the game's reference assemblies — see [plugin/lib/README.md](plugin/lib/README.md) |
| Full stack the easy way | Docker with Compose v2.24+ |

Detailed setup, including the database roles and environment variables:
[docs/SETUP.md](docs/SETUP.md) and [docs/CONFIGURATION.md](docs/CONFIGURATION.md).

```bash
pnpm install            # workspace root; installs shared, backend and web
pnpm --filter @scpsl-trust/shared build   # backend and web import the built shared package
```

## Running the tests

Run the suites of the packages you touched — all of them before opening a PR.

```bash
pnpm --filter @scpsl-trust/shared test        # schemas, policy engine, signing, vectors
pnpm --filter @scpsl-trust/shared vectors:check   # test vectors match the generator
pnpm --filter @scpsl-trust/backend test       # needs PostgreSQL + Redis
pnpm --filter @scpsl-trust/web test           # React components and hooks
pnpm typecheck                                # every package
```

Plugin (C#):

```bash
export PATH=/opt/dotnet:$PATH                 # wherever your SDK lives
dotnet test plugin/ScpslTrust.sln             # Core + the shared test vectors
```

End-to-end, against a real backend and the DevClient: `e2e/run.sh` — see
[docs/E2E.md](docs/E2E.md). `e2e/web-smoke.mjs` drives the browser walkthrough that produced the
README screenshots.

The backend tests create throw-away databases through `TEST_DATABASE_ADMIN_URL`
(default `postgres://scpsl:scpsl@localhost:5432/postgres`); the role needs `CREATEDB`, and the
reset helper needs superuser. CI runs exactly these commands — see `.github/workflows/ci.yml`.

## Test vectors

The cross-language vectors live in **`shared/test-vectors/`** (`signing.json`, `policy.json`,
`proof-codes.json`, `audit-chain.json`, with `shared/test-vectors/README.md` describing the
format). They are generated by `shared/scripts/generate-test-vectors.ts` and consumed by both the
TypeScript tests and the C# xUnit tests, which is what keeps the plugin's policy engine, request
canonicalization and signing byte-identical to the reference implementation.

If you change canonicalization, the policy engine, proof codes or the audit chain:

1. change the reference implementation in `shared/src/`,
2. regenerate: `pnpm --filter @scpsl-trust/shared vectors`,
3. run **both** `pnpm --filter @scpsl-trust/shared test` and `dotnet test plugin/ScpslTrust.sln`,
4. commit the regenerated JSON in the same change.

Never hand-edit a vector file to make a test pass.

## The architecture document is the contract

[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) is binding. The ten rules in §0 are non-negotiable —
most importantly R1: `/player/check` never returns an enforcement action, the SCP:SL server
decides locally. A change that contradicts a rule will not be merged; propose a change to the rule
first, in an issue.

**Any change to the database schema, an API contract, the signing protocol, the permission matrix
or a business rule must update `docs/ARCHITECTURE.md` in the same commit or PR.** Code and
architecture drifting apart is treated as a defect. Where a change is also user-visible, update
the affected document from the README's documentation table (`docs/API.md` is generated from the
OpenAPI document and is checked in CI — regenerate it, don't hand-edit).

## Commits and pull requests

* Work on a branch; never push to `main` directly.
* One logical change per commit. Present-tense subject under ~72 characters, optionally with an
  area prefix — `backend: reject replayed nonces on /player/check`. Explain *why* in the body if
  it isn't obvious.
* Keep the diff to your change. Unrelated reformatting, dependency bumps or file moves belong in
  their own PR.
* Before opening a PR: `pnpm typecheck`, the relevant test suites, and
  `node scripts/check-doc-links.mjs` if you touched documentation.
* In the PR description say what changed, why, how you verified it, and whether
  `docs/ARCHITECTURE.md` needed updating (and if not, why not).
* New behaviour needs tests. A bug fix needs a test that fails without the fix.
* `.editorconfig` and the TypeScript configuration define the formatting; no separate style guide.
  The plugin builds with `TreatWarningsAsErrors`, so warnings are failures.

Small, well-scoped PRs are reviewed much faster than large ones. If you are planning something
big, open an issue first so the design can be discussed before you write it.
